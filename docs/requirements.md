# 個人サイト向け自作CMS 要件定義書

最終更新: 2026-08-26
関連ドキュメント: `architecture.md`（アーキテクチャ設計書）

---

## 1. 背景と目的

### 1.1 背景

現在の個人サイト（[tukaelu/blog](https://github.com/tukaelu/blog)）は、Astroをベースとした静的サイトジェネレータ構成で運用している。

- 記事は `contents/posts` 配下にMarkdown/MDX（`@astrojs/mdx`）として配置し、GitHubリポジトリでバージョン管理している
- フロントマター解析に `gray-matter`、GitHub Flavored Markdown対応に `remark-gfm`、シンタックスハイライトに `rehype-pretty-code`/`shiki` を利用
- 検索は `pagefind` によるビルド時静的インデックス、OGP画像は `satori` + `@resvg/resvg-js` によるビルド時生成
- 日本語タイポグラフィ（自然な改行位置の計算）に `budoux` を利用
- `wrangler deploy` によりCloudflare（Workers/Pages）へデプロイ済み

この構成は、Gitでの変更履歴管理やコードエディタでの執筆に慣れている場合には合理的だが、一般的に静的サイトジェネレータ＋Git運用には以下のような制約が伴う。

- 記事の公開・修正のたびに、コミット・プッシュ・ビルド・デプロイという一連の手順を踏む必要がある
- 専用の管理画面がなく、コードエディタで直接Markdownファイルを編集する運用になる
- スマートフォン等のモバイル端末からの執筆・下書き保存が行いにくい
- いいね・コメントのような動的な機能を持たせるには、外部サービスとの連携や追加のサーバーレス関数実装が必要になりがちで、サイトの構成がGit管理下のコンテンツと外部サービスとに分散しやすい

本プロジェクトは、これらの制約を踏まえ、Cloudflare スタック上に**自分専用の最小限の CMS を内製し、現在の Astro + Markdown + Git 構成を置き換える**ことを目的とする。汎用 CMS 化（コラボレーション機能・監査ログ・マルチテナント対応等）は狙わない。設計にあたっての基本方針は §2 を参照。

### 1.2 目的

1. 記事本文を構造化データとして保持し、独自の表現（リンクカード・コードブロック・埋め込み・図表等）をレンダラー側で型安全に扱えるようにする
2. 管理画面から直接、記事の作成・編集・公開を行えるようにし、コミット・ビルド・デプロイの手順を経ずに記事を公開できるようにする
3. モバイルでの執筆体験を最優先したエディタを用意する
4. Cloudflare の無料〜低コスト枠に収まる運用コストで、いいね・検索・OGP自動生成・RSS配信までを内製する
5. 将来の表現追加（新しいノードタイプ等）を低コストで行える拡張性を持たせる

## 2. 設計方針

Cloudflareスタック上で自作CMSを構築するにあたり、以下を基本方針として設計に反映する。

| 設計上の方針                                                                   | 本プロジェクトでの反映                                                                   |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| HTML/Markdownを中間言語として都度パース・復元し続ける実装は肥大化しやすい      | 記事本文は最初から構造化ノード（Tiptap JSON）として保存し、パース処理を介在させない      |
| モバイルでの改行操作（ソフトブレイク）が汎用エディタでは扱いにくい             | エディタの改行挙動をモバイルでも明示的に操作できるUIを用意する                           |
| コラボレーション機能・監査ログ等の汎用機能は個人サイトには過剰投資になりやすい | 権限管理・監査ログ・コラボ機能は実装しない（単一ユーザー運用）                           |
| 執筆そのものを妨げないミニマルなエディタUIが執筆体験を左右する                 | 管理画面のエディタはタイトル・タグ・アイキャッチ以外の情報を極力視界に入れない構成とする |

## 3. プロジェクトスコープ

### 3.1 対象範囲

- サイト公開面（記事一覧・記事詳細・タグ別一覧・検索。既存サイトの構成に準拠する。詳細は §5.13 参照）
- 管理画面（記事の作成・編集・削除・下書き/予約投稿管理、メディア管理）
- 記事本文エディタ（リッチテキスト、独自ノード対応）
- 付随機能：いいね、全文検索、OGP画像自動生成、RSS配信
- 既存記事（Astro + Markdown管理分）の新CMSへの移行

### 3.2 対象外（本プロジェクトでは扱わない）

- コメント機能（要件から除外。理由は §9 参照）
- 複数ユーザーでの共同編集・権限ロール管理
- 監査ログ・変更履歴の高度な管理（簡易な下書き保存は対象内）
- 他言語対応（i18n）
- ネイティブアプリ
- 広告配信・アフィリエイト管理

## 5. 機能要件

### 5.1 記事管理

- 記事の新規作成・編集・削除
- 下書き（非公開）・予約投稿・公開済みの状態管理（実装方式は `architecture.md` §1.3 参照）
- タイトル・スラッグ・本文・アイキャッチ画像・タグ・概要文（description）の管理
- 自動保存（執筆中のデータ消失防止。頻度が高いため §5.2 のリビジョン記録の対象外とする）

### 5.2 リビジョン管理

- 下書きステータスを含め、記事を**明示的に保存した**タイミング（下書き保存・公開のいずれも）で、その時点の内容をリビジョンとして履歴に記録する。自動保存はリビジョンを作成しない
- リビジョン一覧から、任意のリビジョン間（または特定リビジョンと現在の内容）の差分を表示できる
- 任意のリビジョンを選択して「このバージョンに戻す」操作ができる。この操作は過去のリビジョンを上書き・削除するのではなく、選択したリビジョンの内容を**新しいリビジョン**として保存する（履歴は非破壊で、いつでも遡って確認できる）

### 5.3 タグ管理

- タグの作成・付与・一覧表示
- タグ別記事一覧ページ

### 5.4 リッチテキストエディタ

- Tiptap ベースのリッチテキストエディタ
- 対応ノード：段落、見出し、リスト、引用、画像、コードブロック（言語・ファイルパス指定可）、リンクカード（URLをリッチな埋め込みカードに自動変換）、外部サービス埋め込み（GitHub / YouTube / X（Twitter）/ Instagram）、図表（Mermaid）
- モバイルでの「段落を変えない改行（ソフトブレイク）」を明示的に入力できるUI（専用ボタン等）
- 執筆に集中できるミニマルなUI（参考：しずかなインターネット）

### 5.5 AI執筆支援

外部LLM API（OpenAI、gpt-4o-miniを想定）を用いた執筆支援機能を提供する。実装方式の詳細は `architecture.md` §6.3 参照。

- **校正**：誤字脱字・文法的な誤り・不自然な表現を検出し、修正案を提示する
- **概要文（description）の自動生成**：本文からOGP・メタディスクリプション向けの要約文を生成する
- **構成・アウトライン提案**：タイトルや簡単なメモから、見出し構成の案を生成し、エディタへスケルトンとして挿入できる
- **タイトル提案**：本文（または執筆中のメモ）から、候補となるタイトルを複数生成する
- **スラッグ提案**：タイトルから、URLに使えるスラッグ（英数字・ハイフン）の候補を複数生成する。スラッグ入力は手動が基本だが、この提案をワンクリックで適用できる

### 5.6 メディア管理

- 画像のアップロード・一覧・削除
- アップロード時の最適化（リサイズ・フォーマット変換）

### 5.7 いいね機能

- 記事ごとのいいね数カウント（匿名可、二重カウント防止の仕組みを含む）
- 濫用対策は軽量なレート制限で対応する（詳細は `architecture.md` §8 参照）

### 5.8 検索機能

- 記事タイトル・本文・タグを対象とした全文検索
- 日本語の検索精度に配慮したトークナイズ

### 5.9 OGP自動生成

- 記事タイトル等を元にした OGP 画像（SNSシェアカード）の動的生成
- 生成結果のキャッシュ

### 5.10 RSS配信

- 全記事またはタグ別のRSSフィード配信

### 5.11 モバイル執筆体験

- スマートフォンからの記事執筆・編集がストレスなく行えること（§5.4 と関連）
- レスポンシブな管理画面UI

### 5.12 既存記事の移行

- 既存の `contents/posts` 配下のMarkdown/MDXファイルを、新CMSの構造化データ（Tiptap JSON）形式へ変換する移行スクリプトを用意する
- フロントマター（タイトル・タグ・公開日等）をメタデータとしてD1へ、本文をTiptap JSONへ変換する

### 5.13 公開ページの構成

現行サイト（[nsymtks.com](https://nsymtks.com)）の実際の画面構成を確認した上で、**基本的に既存の構成を踏襲する**。実装方式の詳細は `architecture.md` §4.3 参照。

- **共通レイアウト**：ヘッダー（サイトロゴ＋サイト名、トップページへのリンク）、フッター（コピーライト表記、RSSリンクへの導線）を全ページ共通で表示する
- **トップページ**：公開記事を新しい順に一覧表示する。各記事にタイトル・公開日・**読了時間**・タグ（複数）・抜粋（description）・詳細ページへのリンクを表示し、ページネーションに対応する
- **記事詳細ページ**：タイトル・公開日・タグ・本文を表示する。**見出しから自動生成した目次（アンカーリンク付き）** を本文の前後に配置する。本文中の**脚注**表示に対応する
- **タグ別一覧ページ**：特定タグが付与された記事の一覧を表示する（**確認済み**：既存サイトにはタグ別一覧ページ・タグへのリンクのいずれも存在しない新規追加機能。`architecture.md` §4.3参照）
- **検索**：全文検索の入力・結果表示画面を提供する（**確認済み**：既存サイトに検索機能自体が存在しないため新規追加。UI配置は本プロジェクトで自由に決定する。`architecture.md` §4.3参照）
- **RSSフィード**：`/rss.xml` として配信する（既存踏襲）
- **サイトマップ**：`/sitemap.xml` として配信する（既存踏襲）
- **OGP画像**：記事ごとに専用URLで動的配信する（URLパターンは既存サイトの `/ogp/{slug}.png` を踏襲しない。詳細は `architecture.md` §4.3 参照）
- **404ページ等のエラーページ**：一般的なサイトの体裁として用意する

これら以外の画面要素（新しいセクション、デザインの大幅な変更等）は本プロジェクトのスコープには含めない。デザイン刷新をしたくなった場合は、CMS移行が完了し安定してから別途検討する。

## 6. 非機能要件

### 6.1 パフォーマンス

- Cloudflare のエッジネットワークを活かし、公開ページはできる限りキャッシュを活用する
- OGP画像生成等の重い処理はキャッシュして再計算を避ける

### 6.2 コスト

- 個人サイトの運用として、Cloudflare 各サービスの無料枠内、または月額数百円程度に収める運用を目標とする（詳細な試算は `architecture.md` §12）

### 6.3 セキュリティ

- 管理画面への不正アクセスを防止する認証機構を設ける（Cloudflare Access。`architecture.md` §7 参照）
- いいね投稿等の匿名書き込み機能に対する軽量な濫用対策（レート制限）
- アップロードされる画像に対する基本的なバリデーション（ファイル形式・サイズ）
- AI執筆支援機能で利用する外部LLM APIキーの管理（`architecture.md` §6.3 参照）

### 6.4 可用性・信頼性

- Cloudflare のグローバルネットワークに依存し、単一障害点を極力持たない構成とする
- データのバックアップ方針は `architecture.md` §13 の通り（D1はTime Travelに一任、R2は当面バックアップなし）
- OpenTelemetryによる計装を行い、Mackerelへトレース・ログをエクスポートして監視できること（`spec-ops.md` §8 参照）

### 6.5 保守性・拡張性

- 単一開発者（本人）が無理なく保守できる規模・複雑さに留める
- 新しいエディタノード（表現）の追加が、レンダラー・スキーマの両面で容易であること
- フレームワーク・ライブラリのアップデート追従が過度な負担にならないこと

### 6.6 開発・検証環境

- 本番のCloudflareリソース（D1・R2）に影響を与えずに、ローカルで開発・動作確認ができること（実装方式は `architecture.md` §11.2 参照）
- プルリクエストを作成すると、そのブランチの変更を確認できるプレビュー用URLが自動的に発行されること。プレビューでの操作が本番環境のデータ・トラフィックに影響を与えないこと（実装方式は `architecture.md` §11.3 参照）

### 6.7 テスト方針

- ユニットテストを必須とし、ロジックの複雑な箇所（目次生成、読了時間算出、リビジョン差分、Markdown→Tiptap変換等）を優先的にカバーする
- E2Eテストを導入する。実行環境はローカル（CIジョブ内で`wrangler dev`を起動）とし、PRプレビュー環境への実行は行わない
- 詳細は `spec-testing.md` 参照

## 7. 制約条件

- インフラは Cloudflare スタック（Workers, D1, R2, 必要に応じて KV等）に限定する
- 単一ユーザー運用を前提とし、マルチテナント設計は行わない
- フロントエンド／フルスタックフレームワークは **Nuxt (Vue)** を採用する
- 記事本文は **Tiptap の JSON 構造をそのまま永続化する** 方式を採用する（`architecture.md` 参照）
- AI執筆支援機能は外部LLM API（OpenAI等）を利用するため、上記のCloudflareスタック限定の例外として位置づける。ただし呼び出し経路にはCloudflare AI Gatewayを挟み、キャッシュ・レート制限・ログ管理はCloudflare側で行う（`architecture.md` §6.3 参照）

## 8. 用語集

| 用語           | 説明                                                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Headless CMS   | 表示層を持たず、コンテンツをAPI経由で配信するCMSの形態（例：microCMS）                                                                   |
| Tiptap         | ProseMirror をベースとしたリッチテキストエディタのフレームワーク                                                                         |
| ノード（Node） | Tiptap/ProseMirror における文書構造の構成単位（段落・見出し・コードブロック等）                                                          |
| ソフトブレイク | 段落を変えずに行だけを変える改行（Shift+Enter相当）                                                                                      |
| D1             | Cloudflare が提供する SQLite ベースのサーバーレスデータベース                                                                            |
| R2             | Cloudflare が提供するS3互換のオブジェクトストレージ                                                                                      |
| OGP            | Open Graph Protocol。SNS等でのリンクシェア時に表示されるメタ情報の規格                                                                   |
| リビジョン     | 記事を明示的に保存した時点のスナップショット。差分表示・過去バージョンへの復元に用いる                                                   |
| AI Gateway     | Cloudflareが提供する、外部/内部LLM APIへのリクエストを中継するプロキシ。キャッシュ・レート制限・ログ分析等をコア機能として無料で提供する |

## 10. オープンな論点（今後の検討事項）

現時点で残っている論点は、実装・運用開始後でないと判断できない性質のものに絞られている（詳細は `architecture.md` §15 参照）。画像配信・R2バックアップ方針はいずれも決定済み（§9参照）。
