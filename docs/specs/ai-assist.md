# 機能仕様書：AI執筆支援

最終更新: 2026-08-25
関連ドキュメント: `requirements.md`（§5.5）, `architecture.md`（§6.3）, `spec-article-editing.md`（エディタとの統合ポイント）

---

## 1. 概要

管理画面の記事編集画面に統合される、OpenAI（gpt-4o-mini想定）ベースのAI執筆支援機能。**校正**・**概要文自動生成**・**構成・アウトライン提案**・**タイトル提案**・**スラッグ提案**の5機能を提供する。いずれもCloudflare AI Gateway経由でOpenAI APIを呼び出す、ステートレスな都度生成のAPIとして実装する。

## 2. 関連要件

| 要件定義書の項番 | 内容                                                              |
| ---------------- | ----------------------------------------------------------------- |
| §5.5 AI執筆支援  | 校正・概要文自動生成・構成提案・タイトル提案・スラッグ提案の5機能 |

## 3. 共通仕様

### 3.1 認証・実行基盤

- すべて `/api/admin/ai/*` 配下のエンドポイントであり、Cloudflare Accessの保護対象（`architecture.md` §7）
- OpenAI APIキーはCloudflareのAI Gateway BYOK機能で管理し、クライアント（ブラウザ）には一切露出しない。Worker側からAI Gateway経由でOpenAIを呼び出す
- レスポンスはOpenAIの構造化出力（JSON mode / Structured Outputs）を用いて、パース失敗のリスクを抑える

### 3.2 共通エラーハンドリング

| ケース                            | 挙動                                                                             |
| --------------------------------- | -------------------------------------------------------------------------------- |
| OpenAI API障害・タイムアウト      | エラートースト「AI機能の呼び出しに失敗しました。時間をおいて再度お試しください」 |
| AI Gatewayのレート制限超過（429） | 「AI機能の利用回数が上限に達しました。しばらくしてから再度お試しください」       |
| 構造化出力のパース失敗            | Worker側で1回だけ自動リトライ。再失敗時はエラートーストを表示                    |
| 本文・タイトル未入力での呼び出し  | クライアント側でボタンを`disabled`にし、そもそもAPIを呼ばせない                  |

### 3.3 共通のデータ取り扱い

いずれの機能も生成結果をDBへ保存しない（ステートレス）。画面遷移すると生成結果は失われる想定とする。

## 4. 機能別仕様

### 4.1 校正（確定：段落ノード単位で処理する方式）

**画面仕様**

- エディタツールバーに「校正」ボタンを配置
- 実行するとサイドパネルに校正結果のリストを表示する。各項目：修正前の段落（短く抜粋）・修正後の段落・理由・「適用」ボタン
- 「適用」を押すと、本文中の該当**段落ノードそのもの**を修正後の内容で置き換える

**設計上の判断**：本文をプレーンテキストの塊として送り、返ってきた引用文字列を本文中から検索して置換する方式は、同じ文言が複数箇所にある場合に置換対象を一意に特定できないという問題がある。そこで、**段落（`paragraph`/`heading`等のブロックノード）単位でAIに送り、ノードIDに紐づけて修正後の全文を受け取り、該当ノードそのものを丸ごと置き換える**方式を採用する。ノード単位で処理するため、同一文言が複数箇所にあっても曖昧さが生じない。

この方式を実現するため、Tiptapのブロックレベルノード（`paragraph`/`heading`等）に安定した`id`属性を付与するNode Extensionを追加する（`architecture.md` §4.2の独自ノード一覧とは別に、既存ノードへの属性追加として実装する）。

**API**

`POST /api/admin/ai/proofread`

Request:

```json
{
  "segments": [
    { "nodeId": "n1", "text": "段落1の本文" },
    { "nodeId": "n2", "text": "段落2の本文" }
  ]
}
```

Response 200:

```json
{
  "issues": [
    {
      "nodeId": "n1",
      "original": "修正対象の段落全文",
      "revised": "修正後の段落全文",
      "reason": "誤字／不自然な表現／文法エラー等の分類とひとことコメント"
    }
  ]
}
```

指摘がない段落は`issues`配列に含めない。

**適用時の挙動**：`nodeId`をキーに、エディタ内の該当ノードを`revised`の内容で置き換える。ノードIDによる一意な特定のため、検索のヒット有無を気にする必要がない。ただし、校正実行後にユーザーが該当ノードを削除していた場合は、「このノードは既に削除されています」と表示しリストからグレーアウトする。

### 4.2 概要文自動生成

**画面仕様**

- メタデータパネルの概要（description）欄に「AIで生成」ボタンを配置
- 既に概要が入力済みの場合、上書き確認ダイアログ（「現在の概要を置き換えます。よろしいですか？」）を挟む
- 生成結果はフィールドに反映後、保存前に手動編集可能

**API**

`POST /api/admin/ai/summarize`

Request:

```json
{ "text": "（本文のプレーンテキスト抽出）" }
```

Response 200:

```json
{ "description": "100〜120字程度の要約文" }
```

### 4.3 構成・アウトライン提案

**画面仕様**

- 「構成を提案」ボタンを押すとモーダルが開き、タイトルと簡単なメモ（任意）を入力する
- 生成された見出し構成をプレビュー表示し、「エディタに挿入」で反映する
- 挿入時は**本文全体を置き換える**（末尾追記や既存内容の有無による条件分岐は設けない）。これはユーザーの明示的な操作によるものであり、意図しない上書きが起きても`spec-article-editing.md`のリビジョン機能で復元できるため、過度なガードは不要と判断する

**API**

`POST /api/admin/ai/outline`

Request:

```json
{ "title": "記事タイトル", "notes": "簡単なメモ（任意）" }
```

Response 200:

```json
{
  "headings": [
    { "level": 2, "text": "背景" },
    { "level": 2, "text": "解決方法" },
    { "level": 3, "text": "具体的な実装" },
    { "level": 2, "text": "まとめ" }
  ]
}
```

挿入時、各要素を`heading`ノード（`level`をそのまま使用）としてエディタの本文全体と置き換える形で反映する。

### 4.4 タイトル提案

**画面仕様**

- タイトル入力欄の横に「AI提案」ボタンを配置
- 押すと本文（本文が空の場合は概要欄またはメモ）を元に候補を生成し、ポップオーバーでリスト表示
- クリックでタイトル欄に反映

**API**

`POST /api/admin/ai/suggest-title`

Request:

```json
{ "text": "（本文のプレーンテキスト抽出。空の場合は概要文等）" }
```

Response 200:

```json
{ "titles": ["候補1", "候補2", "候補3"] }
```

### 4.5 スラッグ提案

**画面仕様**

- スラッグ入力欄の横に「AI提案」ボタンを配置（`spec-article-editing.md` §3.2で決定した「スラッグは手動入力が基本」という方針に対する補助機能）
- 押すとタイトルを元に候補を生成し、ポップオーバーでリスト表示
- クリックでスラッグ欄に反映。既存スラッグとの重複チェックは行わず、保存時（`POST /api/admin/articles`）のバリデーション（409）に委ねる（§6未決事項3）

**API**

`POST /api/admin/ai/suggest-slug`

Request:

```json
{ "title": "記事タイトル" }
```

Response 200:

```json
{
  "slugs": ["candidate-slug-one", "candidate-slug-two", "candidate-slug-three"]
}
```

日本語タイトルの単純な音訳ではなく、意味を汲んだ英語表現への変換を意図する（`architecture.md` §6.3参照）。

## 5. データ仕様

該当するDBテーブルはない（すべてステートレスなAPI呼び出し）。

## 6. 処理フロー（共通）

1. ユーザーが対象のAI機能ボタンを押す
2. クライアントは `/api/admin/ai/*` エンドポイントへリクエストを送信する（Cloudflare Accessのセッションが自動的に付与される）
3. Worker（Nitro API Route）がCloudflare AI Gateway経由でOpenAI APIを呼び出す。AI GatewayがキャッシュヒットすればOpenAIへの実呼び出しを行わずにキャッシュから返す
4. 構造化出力をパースし、クライアントへ返す
5. クライアントは結果をUI（サイドパネル／ポップオーバー／モーダル）に表示する
6. ユーザーが個々の提案を選択・適用する（DBへの保存は、通常の記事保存フロー（`spec-article-editing.md` §4）に乗る）

---

## 7. 受け入れ基準

- [ ] 校正ボタンで指摘一覧が表示され、個別に適用できる
- [ ] 概要文自動生成で生成した文章がdescriptionフィールドに反映される
- [ ] 構成提案で生成した見出しがエディタに挿入される
- [ ] タイトル提案・スラッグ提案でそれぞれ候補が表示され、クリックで対象フィールドに反映される
- [ ] OpenAI API障害時・レート制限超過時に、適切なエラーメッセージが表示される
- [ ] いずれの機能も、Cloudflare Accessで認証されていない状態ではアクセスできない

## 8. 決定事項・未決事項

**壁打ちを通じて決定した事項**

| 項目                         | 決定                                                                                                 |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| 生成結果の永続化             | 行わない（ステートレス、画面遷移で消えてよい）                                                       |
| スラッグ提案時の重複チェック | AI提案時点では行わない。保存時のバリデーション（409）に委ねる                                        |
| AI Gatewayのレート制限       | 1分あたり5回                                                                                         |
| 校正の適用方式               | 段落ノード単位でAIに送信し、ノードIDで一意に特定して置き換える（文字列検索による曖昧さを設計上排除） |
| 構成提案の挿入位置           | 本文全体を置き換える。リビジョン機能による復元を安全網とし、過度なガードは設けない                   |

現時点で本ドキュメントに関する未決事項はなし。
