# 機能仕様書：テスト戦略（ユニット・E2E）

最終更新: 2026-08-25
関連ドキュメント: `requirements.md`（§6.7）, `architecture.md`（§1.4, §11.4）

## 1. 概要

本プロジェクトにおけるユニットテスト・E2Eテストの方針、ツール選定、CI統合方式を定義する。ユニットテストは必須、E2Eテストは**ローカル環境（CIジョブ内で`wrangler dev`を起動）に対して実行する方式**を採用する（壁打ちで決定済み。PRプレビュー環境への実行は見送る。§9参照）。

## 3. ツール選定

| 領域                 | 採用技術                    | 理由                                                                                      |
| -------------------- | --------------------------- | ----------------------------------------------------------------------------------------- |
| ユニットテスト       | Vitest                      | Nuxt公式が推奨するテストランナー。Vite/Nitroとの統合が良い                                |
| コンポーネントテスト | `@nuxt/test-utils` + Vitest | Vueコンポーネント・Tiptap Node Extensionのテストに使用                                    |
| E2Eテスト            | Playwright                  | GitHub Actionsとの統合が容易。ローカルサーバーの起動・待受を`webServer`設定で自動化できる |

---

## 4. ユニットテストの方針

### 4.1 対象範囲

優先度の高い順に、以下を対象とする。個人開発の規模を踏まえ、カバレッジ率の数値目標は設定せず、**ロジックの複雑な箇所を優先的にカバーする**方針とする。

| 対象                   | 内容                                                                         | 配置                                                    |
| ---------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------- |
| 目次（TOC）生成        | `heading`ノードからの目次組み立てロジック                                    | `server/utils/toc.test.ts`                              |
| 読了時間算出           | 文字数からの概算ロジック（400字/分）                                         | `server/utils/reading-time.test.ts`                     |
| リビジョン差分         | テキスト差分の生成ロジック                                                   | `server/utils/diff.test.ts`                             |
| Markdown→Tiptap変換    | 移行スクリプトの変換ロジック（`spec-migration.md` §6）                       | `scripts/migrate-from-astro/markdown-to-tiptap.test.ts` |
| スラッグバリデーション | `^[a-z0-9-]+$` 等のルール                                                    | `shared/utils/*.test.ts`                                |
| Tiptap独自ノード       | 各Node Extensionのスキーマ・コマンドロジック（レンダリングではなく構造検証） | `app/components/editor/nodes/*.test.ts`                 |
| Composable             | `useAutosave` / `useAiAssist` / `useLike` のロジック（`fetch`はモック化）    | `app/composables/*.test.ts`                             |

### 4.2 対象外（優先度を下げるもの）

- ロジックを持たない単純な表示コンポーネント（レイアウト、静的な見た目のみのコンポーネント）
- Nitro API Routeのハンドラそのもの（D1/R2バインディングとの結合が強いため、ユニットテストよりE2Eでのカバーを優先する。§5参照）

## 5. E2Eテストの方針（確定）

### 5.1 実行環境

**GitHub ActionsのジョブA内で`wrangler dev`（`nitro-cloudflare-dev`によるD1/R2ローカルエミュレーション）を起動し、そこに対してPlaywrightでテストする。** PRプレビュー環境（Cloudflareへのデプロイ）に対しては実行しない。

理由（壁打ちで整理した比較）：

| 観点             | ローカル（採用）                                                                  | PRプレビュー環境                                                                                                          |
| ---------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| デプロイとの同期 | CIジョブ内で完結するため待ち合わせ不要                                            | Workers Buildsの非同期デプロイ完了を別途待つ仕組みが必要                                                                  |
| 認証             | ローカルはCloudflare Accessをバイパスする設計（`spec-ops.md` §3.4）のため障壁なし | プレビュー全体をAccessで保護する設計（`architecture.md` §11.3）のため、Access Service Tokenの発行・ヘッダー付与が別途必要 |
| データ分離       | CI実行ごとに独立した使い捨て環境                                                  | プレビューのD1/R2はPR間で共有（§11.3）のため、並行実行時にテストデータが干渉しうる                                        |
| 再現度           | Miniflareによるエミュレーション（本物のCloudflareエッジではない）                 | 本番相当の環境で検証できる                                                                                                |

再現度の低さはトレードオフとして許容する。将来的にプレビュー環境に対するE2E（スモークテスト等）を追加したくなった場合は、Access Service Tokenの導入を前提に別途設計する（§9オープンな論点）。

### 5.2 対象シナリオ

| シナリオ         | 概要                                                                                                                                                               |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 記事の作成〜公開 | 管理画面で記事を作成し、保存・公開すると、公開ページの一覧・詳細に表示される                                                                                       |
| 予約投稿         | `published_at`が未来の記事は一覧に表示されず、過去日時に更新すると表示される（実際の時間経過を待つのではなく、DBへ直接シードした未来日時レコードを用いて検証する） |
| リビジョン       | 記事を複数回保存し、リビジョン一覧・差分表示・復元が正しく機能する                                                                                                 |
| いいね           | いいねボタンを押すとカウントが増加し、連打してもカウントが1回分しか増えない                                                                                        |
| 検索             | キーワード検索でヒットする記事が表示される                                                                                                                         |
| AI執筆支援       | 校正・概要文生成・構成提案・タイトル/スラッグ提案の各ボタンを押すと結果が表示され、適用できる（AI呼び出し自体はモックする。§5.3参照）                              |
| 認証             | ローカル環境では管理画面へ認証なしでアクセスできる（`spec-ops.md`の受け入れ基準と対応）                                                                            |

### 5.3 AI執筆支援のモック方針（確定）

E2E実行時に実際のOpenAI APIを呼び出すと、コスト・レイテンシ・非決定性（同じ入力でも応答が変わりうる）の面でCIに不向きである。そのため、**サーバー側のAI Gatewayクライアント（`server/utils/ai-gateway.ts`）に環境変数によるモックモードを持たせる**。

- 環境変数 `AI_MOCK_MODE=true` が設定されている場合、実際にOpenAI/AI Gatewayを呼び出さず、あらかじめ用意した固定のレスポンス（fixture）を返す
- CI（E2E実行時）のみこのフラグを有効にする。ローカル開発時・本番・プレビューでは無効（実際のAPIを呼ぶ）とする
- モックレスポンスは`spec-ai-assist.md` §4の各APIレスポンス形式に準拠したfixtureとして`tests/e2e/fixtures/ai-mock-responses.ts`等に用意する

### 5.4 テストデータ

E2Eで必要な初期データ（記事・タグのサンプル等）は、テスト実行前に専用のシードスクリプト（`scripts/seed-test-data.ts`）でローカルD1へ投入する。本番の移行スクリプト（`spec-migration.md`）とは別物であり、あくまでE2E用の最小限のフィクスチャを目的とする。

## 6. CI統合

`.github/workflows/`に、既存のLint/型チェックとは別（または同一ワークフロー内の別ジョブ）として、以下のステップを持つテストジョブを追加する。

1. リポジトリのチェックアウト・依存関係のインストール
2. `wrangler d1 migrations apply DB --local` でローカルD1にスキーマを適用
3. `scripts/seed-test-data.ts` でE2E用フィクスチャを投入
4. ユニットテスト（Vitest）を実行
5. Playwrightの`webServer`設定により、`wrangler dev`（`AI_MOCK_MODE=true`環境変数付き）を自動起動し、起動完了を待ってE2Eテストを実行
6. テスト失敗時はPlaywrightのHTMLレポートをCIのアーティファクトとしてアップロードする

ユニットテスト・E2Eテストともに、すべてのプルリクエストで実行する（`spec-ops.md` §6.2のプレビューURL発行とは独立したジョブとして動作する）。

## 7. 受け入れ基準

- [ ] `pnpm test:unit`（仮）でユニットテストが実行でき、§4.1の対象がカバーされている
- [ ] `pnpm test:e2e`（仮）でPlaywrightがローカルの`wrangler dev`に対してE2Eテストを実行できる
- [ ] E2E実行時、AI執筆支援のテストが実際のOpenAI課金を発生させない（モックモードで動作する）ことを確認している
- [ ] GitHub Actions上でPRを作成すると、ユニットテスト・E2Eテストの両方が自動実行される
- [ ] E2Eテスト失敗時、Playwrightのレポートがアーティファクトとして確認できる

## 8. 決定事項・未決事項

**壁打ちを通じて決定した事項**

| 項目                  | 決定                                                                      |
| --------------------- | ------------------------------------------------------------------------- |
| ユニットテストツール  | Vitest（+ `@nuxt/test-utils`）                                            |
| E2Eテストツール       | Playwright                                                                |
| E2Eの実行環境         | ローカル（CI内`wrangler dev`起動）。PRプレビュー環境へは実行しない        |
| AI執筆支援のE2Eテスト | サーバー側モックモード（`AI_MOCK_MODE`環境変数）で実際のAPI課金を回避する |
| カバレッジ目標        | 数値目標は設けず、ロジックの複雑な箇所を優先してカバーする                |

**未決事項**

1. E2Eテストシナリオの網羅範囲（§5.2は初期案。実装を進める中で過不足を調整する）
2. 予約投稿のテストで、実際の時刻経過を待たずDB直接シードで代替する方式の実装詳細（時刻をモックするアプローチとの比較検討の余地あり）
3. 将来的にPRプレビュー環境に対するE2E（スモークテスト等）を追加する場合、Cloudflare Access Service Tokenの導入方式
