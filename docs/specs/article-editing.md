# 機能仕様書：記事編集・エディタ・リビジョン管理

最終更新: 2026-08-26
関連ドキュメント: `requirements.md`（§5.1, §5.2, §5.4, §5.11）, `architecture.md`（§1.3, §3, §6.1, §6.2）

---

## 1. 概要

管理画面における記事の作成・編集・削除、下書き/予約投稿、Tiptapベースのリッチテキストエディタ（独自ノード対応）、自動保存/明示保存、リビジョン（変更履歴）の記録・差分表示・復元を提供する。CMSの中核機能であり、他の多くの機能（AI執筆支援、メディア管理等）はこの画面上に統合される。

## 2. 関連要件

| 要件定義書の項番            | 内容                                                     |
| --------------------------- | -------------------------------------------------------- |
| §5.1 記事管理               | 記事CRUD、下書き/予約投稿/公開済みの状態管理、自動保存   |
| §5.2 リビジョン管理         | 明示保存時のスナップショット記録、差分表示、非破壊な復元 |
| §5.4 リッチテキストエディタ | Tiptap、独自ノード、ソフトブレイク                       |
| §5.11 モバイル執筆体験      | モバイルでのストレスない執筆・編集                       |

## 3. 画面仕様

### 3.1 記事一覧画面（`/admin/articles`）

**表示項目**：タイトル、ステータスバッジ、更新日時、タグ

**ステータス判定ロジック**（DB上は`draft`/`published`の2値のみ、UIでは3値に計算して表示する）

| DB上の`status` | `published_at` | UI表示   |
| -------------- | -------------- | -------- |
| `draft`        | —              | 下書き   |
| `published`    | 未来の日時     | 予約中   |
| `published`    | 現在以前の日時 | 公開済み |

**フィルタ・ソート**：ステータス別フィルタ（すべて/下書き/予約中/公開済み）、更新日時降順（デフォルト）

**画面状態**：読み込み中 → 一覧表示 / 記事0件の場合は空状態（「新規記事を作成」への導線を表示）

**アクション**：「新規作成」ボタン押下で `/admin/articles/new` へ遷移

### 3.2 記事編集画面（`/admin/articles/:id` または `/admin/articles/new`）

**レイアウト**

- 上部：タイトル入力欄（プレースホルダー「タイトルを入力」）、その下にスラッグ入力欄（手動入力が基本。AIによるスラッグ提案ボタンを併設し、タイトルから候補を生成できる。詳細は `spec-ai-assist.md` 参照）
- 中央：Tiptapエディタ本体（ツールバー＋本文編集領域）
- サイドパネル（折りたたみ可能、モバイルでは下部シートに変更）：タグ選択、アイキャッチ画像、公開日時、概要文（description）、AI執筆支援へのショートカット、リビジョン履歴へのリンク

**画面状態**

| 状態       | 説明                                                                                           |
| ---------- | ---------------------------------------------------------------------------------------------- |
| 新規作成   | `id`未確定。タイトルまたは本文に最初の変更が入った時点で初回の自動保存を実行し、`id`を発行する |
| 編集中     | 自動保存が一定間隔で動作している                                                               |
| 保存中     | 明示保存API呼び出し中。「保存」「公開」ボタンを`disabled`にし、ローディング表示                |
| 保存完了   | トースト通知（「保存しました」）を2〜3秒表示                                                   |
| 保存エラー | エラーメッセージを表示し、再試行ボタンを提示（§7参照）                                         |

**エディタツールバー**：太字・斜体・見出し（H2〜H4）・箇条書き・番号付きリスト・引用・コードブロック・リンクカード・埋め込み（GitHub/YouTube/X/Instagram）・Mermaid図表・脚注・画像挿入・**ソフトブレイク**（段落を変えない改行、モバイルでの優先表示ボタン）

**モバイル対応**：ツールバーは横スクロール可能なレイアウトとし、ソフトブレイクボタンを含む頻用項目を左側に固定表示する。

### 3.3 リビジョン履歴パネル

記事編集画面のサイドパネルから「履歴」タブでアクセスする。

- リビジョン一覧：`revision_no`降順、作成日時、タイトルのスナップショットを表示
- 各行をクリックすると差分表示画面へ遷移

### 3.4 差分表示画面

- デフォルトでは選択したリビジョンと**直前のリビジョン**の差分を表示する。プルダウンで比較対象を「現在の内容」や任意の他リビジョンに変更できる
- タイトル・概要文・本文（プレーンテキスト抽出後）それぞれについて、追加箇所を緑・削除箇所を赤（取り消し線）で表示する統合差分（unified diff）形式とする
- 「このバージョンに戻す」ボタンを配置。押下すると確認ダイアログ（「現在の内容を上書きし、新しいリビジョンとして記録します。よろしいですか？」）を挟んでから実行する

## 4. API仕様

### 4.1 `GET /api/admin/articles`

一覧取得。

**Query**: `?status=draft|published|all（既定）&page=1&limit=20&sort=updatedAt_desc（既定）`

**Response 200**

```json
{
  "articles": [
    {
      "id": "01J9XAMPLE0000000000000001",
      "slug": "example-post",
      "title": "サンプル記事",
      "status": "published",
      "publishedAt": "2026-08-01T09:00:00Z",
      "updatedAt": "2026-08-20T10:00:00Z",
      "tags": ["tech", "cloudflare"]
    }
  ],
  "pagination": { "page": 1, "totalPages": 3, "totalCount": 42 }
}
```

### 4.2 `GET /api/admin/articles/:id`

編集画面初期表示用の単体取得（実装時に判明した追加エンドポイント。§4.1一覧とは別に、`bodyJson`を含むフル情報を返す）。

**Response 200**

```json
{
  "id": "01J9XAMPLE0000000000000001",
  "slug": "example-post",
  "title": "サンプル記事",
  "description": "概要文",
  "bodyJson": { "type": "doc", "content": [] },
  "status": "draft",
  "publishedAt": null,
  "coverImageId": null,
  "tagNames": ["tech", "cloudflare"]
}
```

**Response 404**：`id`が存在しない場合

### 4.3 `POST /api/admin/articles`

新規作成（＝明示保存）。リビジョンが同時に1件作成される（`revisionNo: 1`）。

**Request**

```json
{
  "title": "新しい記事",
  "slug": "new-post",
  "bodyJson": { "type": "doc", "content": [] },
  "description": null,
  "tagNames": [],
  "status": "draft",
  "publishedAt": null,
  "coverImageId": null
}
```

タグは`tagIds`ではなく`tagNames`（タグ名の配列）で受け取る。サーバー側で既存タグを再利用し、存在しなければ新規作成する（§9決定事項参照。タグ専用の管理API/画面を要件上まだ持たないため、記事編集画面からのフリーテキスト入力で完結させる設計とした）。

**バリデーション**

| フィールド    | ルール                                                      |
| ------------- | ----------------------------------------------------------- |
| `title`       | 必須、1〜200文字                                            |
| `slug`        | 必須、ユニーク、`^[a-z0-9-]+$`                              |
| `bodyJson`    | 必須、Tiptapドキュメント構造（`type: "doc"`のルートノード） |
| `status`      | `draft` \| `published`                                      |
| `publishedAt` | `status`が`published`のとき必須。ISO8601形式                |

**Response 201**：`{ "id": "...", "revisionId": "..." }`（作成された記事の`id`と、作成されたリビジョンの`id`のみを返す。クライアントは送信済みの入力値をそのまま保持しているため、記事オブジェクト全体は返さない）

**Response 409**：`slug`重複時

### 4.4 `PUT /api/admin/articles/:id`

明示的保存（更新）。リクエストボディは4.3と同様。保存の都度 `article_revisions` へ1件追加する。

**Response 200**：`{ "id": "...", "revisionId": "..." }`

### 4.5 `PATCH /api/admin/articles/:id/autosave`

自動保存。部分更新可能（例：`bodyJson`のみ）。**リビジョンは作成しない**。

**Request（例）**

```json
{ "title": "編集中のタイトル", "bodyJson": { "type": "doc", "content": [] } }
```

**Response 200**

```json
{ "savedAt": "2026-08-25T12:34:56Z" }
```

### 4.6 `DELETE /api/admin/articles/:id`

記事削除。`article_tags` / `likes` / `article_revisions` は`ON DELETE CASCADE`で連動削除される。

**Response 204**

### 4.7 `GET /api/admin/articles/:id/revisions`

リビジョン一覧（軽量。`bodyJson`は含まない）。

**Response 200**

```json
{
  "revisions": [
    {
      "id": "rev_00000003",
      "revisionNo": 3,
      "title": "サンプル記事（改題）",
      "status": "published",
      "createdAt": "2026-08-20T10:00:00Z",
      "revertOf": null
    }
  ]
}
```

### 4.8 `GET /api/admin/articles/:id/revisions/:revisionId`

特定リビジョンのフルスナップショット（`bodyJson`含む）を返す。

### 4.9 `GET /api/admin/articles/:id/revisions/:revisionId/diff?against=previous|current|<revisionId>`

**Response 200**

```json
{
  "titleDiff": [
    { "type": "equal", "value": "サンプル" },
    { "type": "removed", "value": "記事" },
    { "type": "added", "value": "投稿" }
  ],
  "descriptionDiff": ["...同様の配列..."],
  "bodyDiff": ["...段落単位のテキスト差分の配列..."]
}
```

### 4.10 `POST /api/admin/articles/:id/revisions/:revisionId/revert`

指定リビジョンの内容を現在の記事へ反映し、新しいリビジョンとして記録する（`revertOf`に復元元のリビジョンIDを設定）。

**Response 200**：`{ "id": "...", "revisionId": "..." }`（§4.3と同様、更新後の記事オブジェクト全体は返さない）

## 5. データ仕様

`architecture.md` §3.2 の `articles` / `article_revisions` / `tags` / `article_tags` テーブル定義を参照。本仕様書での追加バリデーションルールは以下の通り。

| 項目                      | ルール                                                  |
| ------------------------- | ------------------------------------------------------- |
| `slug`                    | 英数字・ハイフンのみ、記事間でユニーク                  |
| `title`                   | 1〜200文字                                              |
| `description`             | 0〜200文字（任意）                                      |
| `body_json`               | ルートノードが`doc`であるTiptapドキュメント構造         |
| リビジョンの`revision_no` | 記事ごとに1から始まる連番（`architecture.md` §3.3参照） |

## 6. 処理フロー

### 6.1 新規作成 → 初回保存

1. `/admin/articles/new` を開くと、クライアント側で空のTiptapドキュメントを初期状態として保持する（`id`はまだ発行しない）
2. タイトルまたは本文への最初の変更をトリガーに、`POST /api/admin/articles` を自動保存相当の内容（`status: draft`）で呼び出し、`id`を発行する
3. 以降はURLを `/admin/articles/:id` へ置き換え、通常の編集フローに合流する

### 6.2 自動保存

- タイトル・本文の変更を検知後、3秒間操作がない、またはフィールドからblurした時点でデバウンスして `PATCH /api/admin/articles/:id/autosave` を呼び出す
- 自動保存はリビジョンを作成しない

### 6.3 明示保存 → リビジョン作成

1. ユーザーが「保存」または「公開」ボタンを押す
2. `PUT /api/admin/articles/:id`（新規記事なら`POST`）を呼び出す
3. サーバー側で `articles` テーブルを更新すると同時に、更新後の状態のスナップショットを `article_revisions` へ1件追加する（`revision_no`は`MAX(revision_no)+1`で採番）

### 6.4 復元

1. リビジョン一覧から対象を選択し「このバージョンに戻す」を押す
2. 確認ダイアログで意図を確認する
3. `POST /api/admin/articles/:id/revisions/:revisionId/revert` を呼び出す
4. サーバー側で、復元元リビジョンのスナップショットを `articles` へコピーし、`revert_of`に復元元IDをセットした新しいリビジョンを追加する
5. クライアント側はレスポンスの記事オブジェクトでエディタの表示内容を更新する

## 7. エラーハンドリング

| ケース                                   | 挙動                                                                                                                                            |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `slug`重複（409）                        | 「このスラッグは既に使用されています」と表示し、フィールドにフォーカスする                                                                      |
| 保存中のネットワークエラー               | トースト通知でエラーを表示し、直前の入力内容はクライアント側の状態に保持したまま失わない。「再試行」ボタンを提示する                            |
| 自動保存の失敗                           | ユーザーに割り込み通知はせず、画面右下に小さく警告アイコンを表示するに留める（執筆の妨げにしない）                                              |
| 同時編集（複数タブ等）                   | 単一ユーザー運用のため楽観的ロックは実装しない。**Last-write-wins**とし、後から保存した内容が優先される。マルチタブでの同時編集は自己責任とする |
| バリデーションエラー（タイトル未入力等） | 保存ボタン押下時にクライアント側で検知し、該当フィールドにエラー表示。API呼び出し自体は行わない                                                 |

## 8. 受け入れ基準

- [x] 記事の新規作成・編集・削除ができる（フェーズ3実装・Playwrightで実地検証済み）
- [x] 下書き・予約投稿・公開済みの3状態が一覧画面で正しく判別・表示される
- [x] 予約投稿した記事が、指定日時を過ぎると自動的に公開ページへ表示される（追加の手動操作不要）（フェーズ2で検証済み）
- [x] Tiptapエディタで独自ノード（リンクカード・コードブロック・埋め込み・Mermaid・脚注）を挿入・編集できる（フェーズ4実装・Playwrightで実地検証済み）
- [ ] モバイル端末でソフトブレイクを明示的に入力できる（ボタンは実装済み、モバイル実機での検証は未実施）
- [x] 一定間隔で自動保存が行われ、ブラウザを閉じても直前の編集内容が失われない
- [x] 明示保存のたびにリビジョンが1件作成される。自動保存ではリビジョンが作成されない
- [x] リビジョン一覧から差分を表示できる（フェーズ5実装・検証済み）
- [x] 過去のリビジョンへ復元すると、新しいリビジョンとして記録され、過去のリビジョンは変更されない（フェーズ5実装・検証済み）

## 9. 決定事項・未決事項

**壁打ちを通じて決定した事項**

| 項目                                              | 決定                                                                                                                                                                                             |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| スラッグ入力方式                                  | 手動入力を基本とする。AIによるスラッグ提案機能を併設する（詳細は `spec-ai-assist.md` 参照）                                                                                                      |
| 自動保存のデバウンス時間                          | 3秒。実装状況に応じて調整可能な値として扱う                                                                                                                                                      |
| リビジョン一覧のページネーション                  | 現時点では不要。件数増加が実運用上の問題になった場合に追加検討する                                                                                                                               |
| タグの入力方式（フェーズ3実装時に決定）           | `tagIds`ではなく`tagNames`（フリーテキストのタグ名配列）で受け取り、サーバー側で既存タグの再利用／新規作成を行う。タグ専用の管理API・画面は要件上未定義のため、記事編集画面への入力で完結させる  |
| 新規作成時の仮スラッグ（フェーズ3実装時に決定）   | `id`未発行時の初回自動保存では、ユーザー未入力でも`draft-{timestamp}`形式の仮スラッグで作成する。明示保存時にユーザー入力のスラッグへ更新される                                                  |
| リビジョン差分の抽出関数（フェーズ5実装時に決定） | FTS5用の`body_text`抽出とは別関数として`extractRevisionText`を実装（architecture.md §6.2の指示通り）。タイトル・概要文は文字単位（`diffChars`）、本文は段落＝改行単位（`diffLines`）で差分を取る |
| 差分の比較方向（フェーズ5実装時に決定）           | `against`の値に関わらず、常に「比較対象(before) → URLで指定したリビジョン(after)」の向きで統一する（`against=current`でも「現在の内容→選択したリビジョン」の向き）                               |

現時点で本機能に関する未決事項はなし。
